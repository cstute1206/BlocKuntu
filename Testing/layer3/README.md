# Layer 3 coverage contract

`cases.json` inventories all 77 IDs in the Layer 3 specification. It contains
the expected behavior, scenario variants, prerequisites, isolation, evidence,
and timing contract. `implementation_bindings` identifies the exact existing
guest/browser/scenario combinations implemented by the smoke and selected group runners. A binding
does not establish that a particular package passed acceptance.

Scheduling is defined by the [current roadmap](../phase-3-roadmap.md). The registry's
`deferred` flag still suppresses the explicitly deferred upgrade case from plans;
other optional catalog cases remain `planned` until implemented. Their presence
in a `full` plan does not make them release requirements.

`../config/layer3-browsers.json` inventories the optional broader matrix: 30 supported
guest/package cells and 12 negative cells. Its `cells` section records six
native smoke layouts using saved P3.1 browser versions/profiles and exact
native-messaging files from the selected package archives. The other 36 cells
retain null source, executable, profile, policy, and Native Messaging fields
until verified in a disposable guest; nulls are not installation recipes.
Observed versions are evidence, never fixed requirements for later runs. The
existing smoke adapters still live in `../fixtures/layer3/browsers.py`.
The [cell cross-check](../results/p31-browser-cells.json) compared those six
entries with saved browser metadata and the exact DEB/RPM/Arch archive listings.

## Read-only planning

From the repository root:

```bash
python3 Testing/scripts/layer3-plan.py --suite smoke --guest ubuntu
python3 Testing/scripts/layer3-plan.py --suite full
python3 Testing/scripts/layer3-plan.py --suite core --guest ubuntu --case VM-AAL-011
python3 Testing/scripts/layer3-plan.py --suite browser-matrix --guest ubuntu \
  --browser firefox-flatpak --output Testing/results/firefox-flatpak-plan.json
python3 Testing/scripts/layer3-groups.py --suite full --guest ubuntu
```

Output files must be new. These commands validate the specification/registry
mapping and enumerate required observations. They do not download packages,
start VMs, install browsers, or claim acceptance. A selected case/browser plan
is labeled `selected`; unknown, deferred, or inapplicable selections fail.
Guest-only checks remain present when filtering a full plan by browser.

Full-plan counts are generated by the planner and change when bindings are added.
They describe a catalog, not a required VM count or a release gate. See the
[current policy](../phase-3-roadmap.md) and the [Ubuntu lifecycle commands](../phase-3.md#ubuntu-lifecycle-commands).

The [Ubuntu desktop commands](../phase-3.md#ubuntu-desktop-commands) add bounded
GUI/private-window/helper groups. `layer3-run-groups.py --scenario` selects explicit
scenario IDs for selected cases; unmatched scenarios or omitted requested cases
fail preflight. The GUI group binds only the four protected mode-change variants
of `VM-EDIT-005`, so its other protected-field variants remain unavailable.
Private-window observations retain their Firefox/Chromium-specific dimensions;
guest-only GUI and helper observations are not duplicated per browser.
GUI, helper and private-window groups also bind those same observations on
Fedora and CachyOS; select one guest per invocation. Private groups use native
Firefox/Chrome on Fedora and Firefox/Chromium on CachyOS. Adapter availability
does not establish a saved VM pass; consult the validation report.
The native private groups now have accepted passes on all three guests; the
[Fedora/CachyOS audit](../results/private-port-20261005/audit-final.json) verifies
12 selected observations plus 21 smoke prerequisites per guest and cleanup.
Broader matcher/lifecycle groups remain Ubuntu-only. See the
[portability commands](../phase-3.md#fedora-and-cachyos-desktop-checks).

`layer3-groups.py` adds conservative clone boundaries to a plan. The known
whole-smoke sequence remains one fresh clone per guest. Selected isolated
Ubuntu cases are also runnable, each on its own fresh clone. The ten native
Firefox/Chrome observations for `VM-WEB-003–007` form one explicitly shared
fresh-clone group with browser-specific routes and rules. `VM-WEB-001` is a
separate two-browser Ubuntu group with guest-local DNS and managed-hosts
transition evidence. Other observations
receive separate fresh-clone groups with `runnable: false` until a tested
scenario executor and isolation rule exist. Full catalog plans are not a recommendation to create one VM per observation.
Implemented observations in these plans have a bounded planning budget from
their scenario plus desktop setup and teardown deadlines; planned observations
have a null budget. A budget does not make a group runnable.

## Serialized smoke and isolated groups

`layer3-run-groups.py` is the execution boundary for known groups. It verifies
the complete selection and every selected Layer 2 package against the local
provenance report before starting a VM. It rejects unimplemented groups,
previously used run IDs, and an existing group-run directory. Run it from the
repository root with a new prefix:

```bash
python3 Testing/scripts/layer3-run-groups.py --suite smoke \
  --run-prefix p31c-36269349435 \
  --verified-inputs Testing/results/package-ci/github-36269349435/verified-inputs.json \
  --preflight-only
python3 Testing/scripts/layer3-run-groups.py --suite smoke \
  --run-prefix p31c-36269349435 \
  --verified-inputs Testing/results/package-ci/github-36269349435/verified-inputs.json
```

The second command runs one fresh clone per guest, sequentially. The isolated
Ubuntu cases can be batched with a new prefix; each receives a separate clone:

```bash
python3 Testing/scripts/layer3-run-groups.py --suite core --guest ubuntu \
  --case VM-WAL-001 --case VM-WAL-005 --case VM-AAL-001 \
  --run-prefix p31isolated-new \
  --verified-inputs Testing/results/package-ci/github-36269349435/verified-inputs.json
```

Run the bounded Ubuntu website matcher group with all five case IDs:

```bash
python3 Testing/scripts/layer3-run-groups.py --suite core --guest ubuntu \
  --case VM-WEB-003 --case VM-WEB-004 --case VM-WEB-005 \
  --case VM-WEB-006 --case VM-WEB-007 \
  --run-prefix p32web-new \
  --verified-inputs Testing/results/package-ci/github-36269349435/verified-inputs.json
```

This selection first runs the 21-observation smoke prerequisite, then records
the ten P3.2 browser observations in a separate checkpoint. A group pass
requires the visible blocked page and expected rule name, positive/near-miss
assertions, screenshots, case budgets, package provenance, base integrity,
and guarded clone removal. It is selected Ubuntu coverage, not a core-suite pass.

The domain and covered-subdomain case uses its own fresh clone and local DNS
forwarder so BlocKuntu's managed `/etc/hosts` entries can be distinguished
from the fixture's baseline resolution:

```bash
python3 Testing/scripts/layer3-run-groups.py --suite core --guest ubuntu \
  --case VM-WEB-001 --run-prefix p32domain-new \
  --verified-inputs Testing/results/package-ci/github-36269349435/verified-inputs.json
```

This group checks DNS `127.0.0.1` before the rule, `0.0.0.0` for its domain
and `www` subdomain after activation, unchanged near-miss resolution, and
visible browser block pages with the expected rule. Public DNS is forwarded
through the clone's original resolver during published-store onboarding.

Each group uses `vm-acceptance.py` and retains its own result
bundle. `results/<prefix>-group-run/summary.json` is updated after each group;
the adjacent logs retain stdout and stderr. A nonzero exit or missing/invalid
result stops later groups. The smoke verifier requires all 21 dimensioned smoke
observations, exact package checksum/version/commit, harness manifest, clone
identity and removal, Phase 0 identity, and base-integrity evidence. The
isolated-case verifier requires its exact scenario checkpoint, case-specific
assertion evidence, package provenance, Phase 0 identity, base integrity, and
removed clone. A failure
does not trigger a retry or remove uncertain clone state; inspect its evidence
and owner record before choosing a new run prefix. These are group-specific
results, not full Layer 3 acceptance or a live libvirt inventory check.

To recheck saved smoke group runs, including a retry, and verify current immutable
bases and libvirt inventory:

```bash
python3 Testing/scripts/layer3-audit-groups.py \
  --summary Testing/results/p31c-36269349435-group-run/summary.json \
  --summary Testing/results/p31d-36269349435-group-run/summary.json \
  --live --output Testing/results/new-group-audit.json
```

The latest attempted group for each selected guest must pass. Earlier failed
attempts remain visible; every recorded owner must have removed copied
storage. An audit without `--live` reports `incomplete`, since saved files
cannot establish current base and libvirt state.

This audit CLI accepts smoke summaries only. Selected integration groups use the
case-specific bundle verifier; a final selected-run audit must also check current
harness files, immutable bases and live clone removal. The bounded Ubuntu batch
records that check in its [validation report](../reports/phase-3-validation.md).

## Result boundary

`scripts/layer3_contract.py` validates the data and builds plans keyed by case,
guest, browser package, and scenario. Its observation checker rejects duplicate
or misattributed results and passes claimed for unimplemented observations;
missing/skipped/blocked observations remain incomplete. It always returns
`acceptance_status: not_evaluated`: package provenance, actual evidence,
dependencies, clone integrity, and repeatability still need the VM runner.

P3.1 runtime integration is in progress. `vm-acceptance.py` now builds a
registry-derived plan before cloning, uploads the smoke plan, and checks the
guest and host observations using exact guest/browser-package/scenario keys.
The executor runs the full smoke sequence for smoke selections. `--suite`
accepts the four planned suite names, but selections containing unimplemented
observations fail before a VM is created. `--case` is usually a diagnostic
projection of the full smoke sequence; its result has `coverage_scope: selected`
and a distinct suite name, so it cannot count as complete suite acceptance.
The isolated Ubuntu observations and native-browser groups documented in the
[runbook](../phase-3.md) are executable. Other unbound core and browser-matrix
observations remain unavailable. Failed setup and
unexpected rows invalidate the coverage gate. The modified harness passed
[one fresh smoke regression per guest](../results/p31-runtime-regression.json);
this is a source/runtime checkpoint, not full Layer 3 acceptance.
The later [budget and dependency regression](../results/p31b-runtime-regression.json)
also passed one fresh run per guest under identical current harness files.

For example, `--suite core --case VM-WEB-002` runs the existing smoke sequence
and reports the selected two browser observations; `--suite full` currently
fails preflight with the first unimplemented observations. Saved P3.0 reports
remain evidence for their original harness, not for the modified runner.

The smoke plan now carries a bounded budget for each implemented scenario.
The runner derives the guest-group and root-supervisor limits from those
budgets plus the registry's setup/teardown deadlines. Current values are
2,520 and 470 seconds, respectively; they cap the harness and do not shorten
BlocKuntu's timers. Service, GUI, browser, and process dependency failures
stop downstream smoke actions; the result gate records missing actions as
blocked. New scenarios require their own verified budgets and isolated
execution groups before becoming automated.
The process supervisor checkpoints each completed process case atomically. If
it exits before publishing completion, the guest retains finished rows, marks
missing cases blocked, and fails the suite; the host collects the checkpoint
and process journal for diagnosis.

Run the contract regression checks with:

```bash
python3 Testing/scripts/test_layer3_contract.py

python3 Testing/scripts/test_layer3_groups.py

```

## Smoke repeatability evidence

After executing a run series, check its saved smoke results with:

```bash
python3 Testing/scripts/check_vm_smoke.py --prefix p30-36269349435 \
  --verified-inputs Testing/results/package-ci/github-36269349435/verified-inputs.json \
  --output Testing/results/p30-smoke-pairs.json
python3 Testing/scripts/test_check_vm_smoke.py
```

The checker inventories every matching run directory and evaluates the latest
two chronological attempts per guest. It rejects missing observations, setup
failures, duplicate observations, reused clone identities, and differing package,
harness, browser/extension, or base records. Earlier failures remain visible;
they do not invalidate two later comparable passes. Incomplete attempt evidence
prevents completion rather than being ignored. Output files must be new.

This is an offline check of saved P3.0 smoke evidence, not full Layer 3
acceptance. It does not rehash installed guest binaries or contact libvirt;
artifact verification belongs to the runner, and final live clone inventory
must still be checked separately. It leaves the executable smoke harness
unchanged so paired runs remain comparable.

When implementing new coverage, add an explicit binding for the implemented
scenario and guest/package dimension, and extend the executor and tests in the
same change. Do not infer implementation from a browser family or a broad case
status. Updating expected behavior requires updating the specification and the
registry together; drift is rejected by the planner.
